### B.1 Disponibilità su repository privato personale: GitHub Free vs GitHub Pro

*(Domanda aperta per il titolare: **il tuo account GitHub è oggi su piano Free o GitHub Pro?**)*

- **[VERIFICATO — fonti 1, 5, 6, 8]:** Su un **repository privato di un account personale**:

### B.3 Etichette `sigillo-*` e `riserva-*` non cancellabili e non spostabili (Tag Rulesets)

- **[VERIFICATO — fonti 2, 3]:** Si crea un **Tag Ruleset** separato dal Branch Ruleset (`Settings` → `Rules` → `Rulesets` → `New ruleset` → `New tag ruleset`):
  - **Target tags:** `Include by pattern` (sintassi `fnmatch`, dove `*` non attraversa `/`) con i due pattern:
    - `sigillo-*`
    - `riserva-*`
  - **Regole da attivare:**
    - **`Restrict deletions`** (impedisce di cancellare i tag esistenti);
    - **`Restrict updates`** (impedisce di spostare / sovrascrivere con `git push --force` i tag esistenti).
  - **Regola da lasciare DISATTIVA (o riservata al solo titolare):**
    - **`Restrict creations`** — se lasciata disattiva, si possono creare nuovi tag `sigillo-H-002-v3`, `riserva-apertura-1`, ecc. al momento opportuno, ma una volta creati nessuno può più spostarli né cancellarli. Se invece si vuole che solo il titolare (via bypass) possa anche *creare* tag con quei prefissi, si può attivare `Restrict creations` tenendo `Repository admin` nella bypass list.

### B.4 Come rendere registrato e visibile uno scavalcamento del titolare

1. **`Rule Insights` (nativo GitHub Pro) `[VERIFICATO — fonte 4]`:** in `Settings` → `Rules` → `Insights` GitHub registra una timeline filtrabile di tutti gli eventi sui ruleset: **`Passed`**, **`Failed`** e **`Bypassed`** (con utente, data/ora, ramo o tag e regola scavalcata).
2. **`Security log` personale `[VERIFICATO — fonte 9]`:** in `Settings` dell'account personale → `Security log` restano tracciate le modifiche alla configurazione dei ruleset e delle protezioni (`repository_ruleset.*`, `protected_branch.*`), così anche disattivare temporaneamente una regola lascia traccia.
3. **Nota sulla visibilità per i revisori `[DEDOTTO]`:** *Rule Insights* è visibile solo agli admin del repository (non agli agenti o al DGS via git) e il *Security log* ha finestra temporale finita. Per rendere ogni scavalcamento permanente e verificabile nella storia del progetto, conviene affiancare la prassi di **registrare ogni bypass in `REGISTRO-MODIFICHE.md` / `DECISIONI.md`** (con data, motivo e SHA del commit), così che il confronto con *Rule Insights* durante un audit resti immediato.

### B.6 Che cosa resta scoperto (limiti noti + nuovi limiti trovati)

- **Limiti noti (confermati):**
  1. **Repository locale e registri locali prima del push (`#90`):** un file JSON riscritto coerentemente in locale prima del primo push non è visto da GitHub.
  2. **Riscrittura locale di `refs/remotes/origin/...` + `reflog` (`#98`):** finché il codice gira a rete bloccata senza `git fetch`, vede solo il clone locale; la divergenza emerge però al primo `git fetch` o `git push` verso il ramo protetto.
  3. **Cache Dukascopy locale (`.bi5`):** i dati reali stanno fuori da GitHub (`brain/dati/reali/`), quindi la protezione del ramo non copre alterazioni locali della cache prima dello sviluppo.
  4. **`avvio.py` e comandi sul Mac:** modificare il lanciatore in locale o lanciare `python3 -c` aggira i controlli sul Mac (la difesa è la riproduzione indipendente e il confronto col codice su GitHub).
- **Limiti aggiuntivi rilevati in Compito B:**
  5. **Piano GitHub Free `[VERIFICATO]`:** su Free, un repository privato personale ha **zero** protezione lato server (né ruleset né branch protection né `CODEOWNERS`).
  6. **Condivisione delle credenziali del titolare con gli agenti `[DEDOTTO]`:** se un agente sul Mac usa la stessa chiave SSH o lo stesso PAT con permessi `admin` dell'account del titolare, **eredita il privilegio di bypass del titolare**! Per rendere efficace D-49 occorre che gli agenti lavorino su rami non protetti (`rev/*`, `feat/*`) o usino un token fine-grained **senza** permesso di bypass/push sui rami protetti.
  7. **Modifica di `.github/workflows/test.yml` o `.github/scripts/esegui_test.py` nello stesso branch `[DEDOTTO]`:** con `Required approvals = 0` (Alternativa B) una PR potrebbe modificare `test.yml` per far passare check finti se il titolare non controlla il diff prima del merge; i *required workflows* centralizzati di organizzazione non esistono su un account personale Pro.
  8. **Retention limitata dei log GitHub `[DEDOTTO]`:** *Rule Insights* e *Security log* non sostituiscono un registro versionato nel repository per audit a distanza di mesi/anni.
